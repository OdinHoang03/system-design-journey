## 故事

NoteNest 有一个公开笔记的搜索框。用户输入“nodejs ...”时得自己记住整个短语,不少人干脆放弃。小明想让搜索框**边输入边提示**:输入 `no` 就显示 `notion`、`node js`、`note taking`。听起来简单,但每按一个键都是一次请求,一百万用户同时输入会产生海量查询,而且每条建议必须在用户按下一个键之前返回。

## 核心概念

### 1. 需求

**功能:** 给定一个**前缀**,返回以它开头的最热门的 5 条建议;支持带声调的越南语和多语言;(可选)个性化、拼写纠错。

**非功能:** **非常快**(p99 低于约 100 ms,因为输入是连续的);高可用;建议能在几分钟到几小时内反映趋势(不要求即时);过滤不当内容。

**不在范围内:** 全文搜索(第 15 课)、搜索结果排序。

### 2. 估算(见第 8 课)

- 每日活跃用户 1000 万,每人搜索 10 次 × 平均 4 次按键会发请求 ⇒ 4 亿请求/天 ≈ **5,000/秒**,峰值约 **25,000/秒**。
- 1 亿个不同的查询,每个约 30 字节 ⇒ 原始数据约 **3 GB**;前缀树会大几倍,但仍能**装进**几台机器的内存。

结论:**读极多、数据小**;数据可以放在内存里,缓存效果极好。

### 3. API

```http
GET /api/v1/suggest?q=no&lang=zh&limit=5
→ 200 {"suggestions": ["notion", "node js", "note taking", "notebook", "nodemailer"]}
```

浏览器在用户停止输入约 100–150 ms 后才发送(**防抖**),有新按键时取消旧请求。

### 4. 总体设计

![搜索联想](/img/diagrams/case-autocomplete.svg)

*本项目自绘示意图。*

有两条相互分离的路径:

- **服务路径(读,快):** 浏览器 → 缓存(前缀 → top 5)→ trie 服务器。大部分请求命中缓存。
- **数据路径(写,慢):** 查询日志 → 汇总计数 → 构建新的 trie → 推送到 trie 服务器。

把两条路径分开是关键:trie 不会随每次查询更新,读路径不受任何干扰。

### 5. 深入

**Trie(前缀树)。** 每条边是一个字符;从根到某个节点的路径就是一个前缀。查找长度为 `L` 的前缀耗时 `O(L)`,与查询总量无关。

```text
        (根)
          n
          o
        /   \
       d     t
       e     e → "note" (880)
       js    book (310), taking (640)
```

如果每次查找都得遍历整棵子树才能找出 top 5,靠近根的节点(比如 `n`)有数百万后代:太慢了。解决办法:**在每个节点预先存好 top-k**(其子树中最好的 5 条建议及分数)。这样查找只需走 `L` 步再读现成的列表:`O(L)`。代价是额外的内存(可以只存查询 id,并裁掉极少见的分支来缩减)。

**排序分数。** 基础是最近一个时间窗内的查询频率。实际还会混入:新近度(随时间衰减的权重,指数衰减)、建议的点击率、语言/地区,以及敏感内容过滤(构建 trie 时应用黑名单)。

**近实时更新。** 用单独的批处理作业,根据汇总后的查询日志,每隔几分钟到几小时重建整棵 trie,然后**整体替换**(蓝绿发布,第 22 课),让服务器始终读取一致的 trie。对需要更快上榜的热点趋势,再加一个由事件流(第 16 课)更新的小型**叠加层(overlay)**,在服务时与 trie 结果合并。

**缓存。** 短前缀(1–3 个字符)的取值很少却被频繁查询:在浏览器(`Cache-Control: max-age`)、CDN 和 Redis(第 2、4 课)里缓存。仅浏览器缓存就能去掉大部分重复请求。

**扩展。** 数据很小,所以每台机器都可以持有**整棵 trie**;只需复制副本并做负载均衡(第 3 课)。如果数据超出内存,就**按前缀分片**(如 `a–f`、`g–m`…)。注意倾斜:常见字母重得多,要按实际负载切分,而不是按字母表平均切。

**其他细节。** 输入规范化(转小写、可选去除声调、Unicode NFC)、个性化建议(把个人历史与全局 top 混合)、用编辑距离做拼写纠错。

## 取舍

| 选择 | 得到 | 失去 |
|---|---|---|
| 每个节点存 top-k | 查找 `O(L)`,非常快 | 占内存;分数变化时要重建 |
| 查询时遍历子树 | 内存更少,始终最新 | 短前缀时很慢 |
| 批量重建 trie | 简单,读不被加锁 | 建议滞后几分钟到几小时 |
| 流式叠加层 | 能跟上热点趋势 | 多一条要运维的数据路径 |
| 浏览器/CDN 重度缓存 | 大幅降低负载,速度快 | 建议可能滞后几分钟 |
| 每台机器持有整棵 trie | 简单,无需跨机调用 | 受单机内存限制 |
| 按前缀分片 | 数据可任意增长 | 负载倾斜;更复杂 |
| 个性化 | 建议更相关 | 难缓存;要保护更多敏感数据 |

## 常见错误

- 每次按键都发请求,不防抖也不取消;后端被冲击,响应还会乱序到达。
- 在读路径上按每次查询直接更新 trie;锁竞争和延迟飙升。
- 不存 top-k,每次请求都遍历整棵子树。
- 不过滤敏感内容,或让查询日志里的个人信息(邮箱、手机号)变成建议展示给别人。
- 按字母表平均分片,导致某个分片(`s`、`t`、`n`…)承受数倍负载。
- 忘记 Unicode 规范化:同一个带声调的词用两种编码输入,得到两种不同结果。
- 只在服务器上测 p99,而不是从用户侧测。
