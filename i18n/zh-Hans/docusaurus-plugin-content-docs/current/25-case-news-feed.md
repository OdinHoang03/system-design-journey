> 一条动态,上百万人观看:这份工作应该在写入时做,还是在读取时做?

## 故事

NoteNest 新增了关注功能:用户互相关注,打开首页就能看到所关注的人最新发布的公开笔记。起初小明只写了一条查询:取出关注列表,再取这些人的最新动态,按时间排序。关注 100 个人时没问题。后来一位拥有 200 万粉丝的知名作者发了帖,上百万人同时打开 App。每次打开页面要几百次查询,数据库被堵死。

套路照旧:**需求 → 估算 → API → 总体设计 → 深入 → 取舍**。

## 核心概念

### 1. 需求

**功能:** 发帖;关注/取消关注;查看所关注者的动态流,最新的在前;无限滚动。

**非功能:** 信息流加载快(约 200 ms 以内),新帖几秒内出现(可接受最终一致,[第 5 课](./05-database-replication-sharding.md)),高可用,能扛住拥有数百万粉丝的账号。

**不在范围内:** 机器学习排序、广告、富媒体。

### 2. 估算

- 1000 万 DAU,每人每天打开信息流 5 次 ⇒ 5000 万次读取 ≈ **每秒 600 次读**,峰值约 3,000(第 8 课)。
- 每人每天发 0.5 条 ⇒ 每天 500 万条 ≈ **每秒 60 次写**。
- 平均每人 200 个粉丝 ⇒ 写扩散:60 × 200 = **每秒 12,000 次插入**;一位 200 万粉丝的作者发一条帖就产生 200 万次插入。
- 信息流缓存:1000 万人 × 500 个帖子 id × 8 字节 ≈ **40 GB**,小型 Redis 集群即可。

结论:系统是**读多**的,但粉丝数分布极度倾斜(少数超大账号)。难点就在这里。

### 3. API

```http
POST /api/v1/posts          {"text": "..."}      → 201 {"id": "p123"}
POST /api/v1/follow/{user}                         → 204
GET  /api/v1/feed?limit=20&after=<cursor>          → 200 {"items": [...], "next": "<cursor>"}
```

信息流使用**游标分页**(第 9 课),因为新帖不断出现在顶部,用 offset 会让分页错位。

### 4. 两种核心策略

![信息流扩散](/img/diagrams/case-news-feed.svg)

*本项目自绘示意图;思路参考自 Twitter 的[“Timelines at Scale”演讲](https://www.infoq.com/presentations/Twitter-Timeline-Scalability/)和 [system-design-primer](https://github.com/donnemartin/system-design-primer)(CC BY 4.0)。*

**读扩散(拉)**:读取时,取出关注列表,取每个人的最新帖子,合并并排序。写很便宜(只存帖子);关注的人多时,读既昂贵又慢。

**写扩散(推)**:发帖时,把帖子 id 插入**每个粉丝自己的信息流**(Redis 中的一个列表)。读取极快(取一个现成的列表),但写入昂贵:大 V 的一条帖子变成上百万次插入,其中很多白白浪费在从不打开 App 的人身上。

### 5. 深入:混合模型

实际中会**混合使用**:

- 普通用户(粉丝少):**推**。帖子进入队列([第 6 课](./06-message-queue.md)),*扩散 worker* 把 id 插入各粉丝的信息流缓存,异步进行,发帖者无需等待。
- 大 V(超过阈值,如 10 万粉丝):**不推**。他们的帖子只存一份。
- 读取时:取用户现成的信息流,再**拉**取其所关注大 V 的最新帖子,按时间合并。

**信息流缓存只存 id。** 信息流是帖子 id(和时间戳)的列表,截断在约 500 条。读取时从帖子/用户缓存中“填充”(hydrate)正文和作者名([第 4 课](./04-cache.md));这样避免把内容复制上百万次,也让编辑/删除只需在一处进行。

**不活跃用户。** 不向长期没打开 App 的人推送;等他们回来时,通过拉取重建信息流。这能节省大量写入。

**数据。** 帖子按 `post_id`/作者分区;关注关系双向存储(谁关注了谁、谁被谁关注),因为扩散需要粉丝列表,而拉取需要关注列表([第 5 课](./05-database-replication-sharding.md))。

**删除与取关。** 信息流缓存里可能有已删除的 id;填充时跳过不存在的 id,并逐步清理。取关后,缓存刷新前残留几条帖子是可以接受的。

**排序。** 按时间倒序(类似 Snowflake 的时间有序 id 很有用)。游标保存上一页最后一项的 id/时间戳。

## 取舍

| 选择 | 得到 | 失去 |
|---|---|---|
| 读扩散 | 写便宜,始终最新 | 读慢,查询负载大 |
| 写扩散 | 读极快 | 大 V 带来写入风暴;为不读的人白做工 |
| 按粉丝数阈值混合 | 兼顾两者 | 更复杂;读取时要合并 |
| 信息流只存 id | 省内存,编辑/删除容易 | 多一步填充 |
| 异步扩散 | 发帖快 | 他人的信息流里晚几秒才出现 |
| 信息流截断为 500 条 | 内存有上限 | 滚动太远要查数据库 |
| 跳过不活跃用户 | 节省写入 | 首次回访较慢 |

## 常见错误

- 纯推送,结果被拥有上百万粉丝的账号压垮。
- 把完整帖子内容复制进每个人的信息流。
- 使用 offset 分页;新帖导致重复/遗漏。
- 在发帖请求里同步做扩散,发帖者要等。
- 没有阈值,也没有对“热点用户”的特殊处理。
- 填充时忽略删除、拉黑和隐私。
