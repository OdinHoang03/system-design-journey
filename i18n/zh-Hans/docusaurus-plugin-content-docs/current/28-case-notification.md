> 把对的消息,通过对的渠道,只送给对的人一次。

## 故事

NoteNest 上线了笔记共享。有人邀请你加入共享笔记时,你应该收到通知:手机推送、邮件,有时还有短信。起初每个功能都用自己的方式调用邮件服务商。后来事故接连出现:某个 worker 中途重启,把整批重发了一遍,成千上万的人收到两封一样的邮件;登录验证码(OTP)被堵在几千封营销邮件后面,迟到了五分钟。小明决定抽出**一个共用的通知系统**。

熟悉的流程:**需求 → 估算 → API → 总体设计 → 深入 → 取舍**。

## 核心概念

### 1. 需求

**功能:** 通过推送(iOS/Android)、邮件、短信发送通知;用户可按渠道和类型开关;按语言的模板;立即发送或定时发送。

**非功能:** 紧急通知(OTP)在几秒内送达;**不重复发送**;批量发送时不拖慢紧急通知;易于新增渠道;可追踪送达状态。

**不在范围内:** 模板编辑器设计、内容 A/B 测试。

### 2. 估算

- 1000 万用户,每人每天平均 5 条通知 ⇒ 5000 万/天 ≈ 平均 **600/秒**,峰值几千/秒(见第 8 课)。
- 一次营销活动 1 小时发 1000 万条 ≈ 额外 **2,800/秒**,而且不能挤占 OTP。
- 日志保留 90 天 × 5000 万 × 约 300 字节 ≈ **1.3 TB**。

结论:负载中等,但**向外发送既慢又不可靠**(服务商会限速,也会出现临时故障)。需要队列来解耦并吸收突发流量。

### 3. API

```http
POST /api/v1/notifications
Idempotency-Key: 7b1e...
{"user_id": 42, "type": "note_invite", "priority": "normal",
 "data": {"note_title": "本周计划", "inviter": "阿兰"}}
→ 202 {"id": "n_91c"}
```

返回 `202 Accepted`:发送异步进行(第 6 课)。`Idempotency-Key` 让调用方的服务重试时不会产生第二条通知(第 9 课)。

### 4. 总体设计

![通知系统](/img/diagrams/case-notification.svg)

*本项目自绘示意图。*

1. **通知 API** 接收请求,检查**用户偏好**(这个渠道关了吗?是否在免打扰时段?),去重并限流(第 11 课)。
2. 选择渠道,按用户语言用**模板**渲染内容,然后推入**每个渠道各自的队列**。
3. 每个渠道的 **worker** 取消息,调用服务商(推送用 APNs/FCM,另有邮件服务商和短信服务商),并记录结果。
4. 临时失败会重试;次数用完后进入**死信队列**等待人工查看。

### 5. 深入

**优先级。** 为每个级别使用独立队列(或优先级类别):`critical`(OTP、安全告警)、`normal`、`bulk`(营销活动)。`bulk` 的 worker 要限速,以免耗尽服务商的整个配额。活动进行时 OTP 依旧飞快,靠的就是这一点。

**去重。** 消息队列通常是**至少一次**(at-least-once,第 6 课):同一条消息可能被投递两次。对策:
- 每条通知有**稳定的 `notification_id`**(由幂等键派生)。
- 发送前,worker 在 Redis 上执行 `SET dedup:{id} NX EX 86400`;若键已存在则跳过。
- 服务商支持的话,把这个 id 也作为对方的幂等键传过去。
- 要明白调用外部系统时无法保证绝对的“恰好一次”:最终采用**至少一次 + 去重**,让实际效果接近恰好一次。

**带退避的重试。** 在 1 秒、5 秒、30 秒、5 分钟…之后重试,并加抖动(第 17 课)。区分临时错误(超时、5xx、被限速)与永久错误(设备令牌已失效、邮箱不存在):永久错误不再重试,并标记该令牌/邮箱以便清理。

**偏好与合规。** 维护 `preferences(user_id, channel, type, enabled)` 表;营销邮件必须带退订链接(RFC 8058 描述了一键退订)。交易类/安全类消息可以忽略营销偏好,但不能违背法律要求。

**定时发送。** 按发送时间存入表或有序集合;定期扫描器把到期的项推入队列。若要按用户所在时区发送,创建时就换算成 UTC 时刻。

**状态追踪。** 根据服务商的响应和 webhook 记录事件链 `queued → sent → delivered → opened/failed`。使用只追加的日志,再异步汇总。

## 取舍

| 选择 | 得到 | 失去 |
|---|---|---|
| 每个渠道独立队列 | 慢或出错的渠道不拖累其他渠道;可独立扩展 | 要运维的组件更多 |
| 每个优先级独立队列 | OTP 始终很快 | 需要调节公平性,避免 bulk 被无限饿死 |
| 至少一次 + 去重 | 不丢消息,重复极少 | 需要去重存储(Redis)和合理的 TTL |
| 至多一次 | 绝不重复 | 可能丢消息,OTP 不能接受 |
| 积极重试 | 送达率高 | 可能冲击服务商,迟到的发送惹人烦 |
| 共用内容模板 | 易改易翻译 | 要管理模板版本 |
| 使用外部服务商 | 开发快,基础设施现成 | 产生依赖、按条计费,还需第二家服务商作备份 |

## 常见错误

- 所有类型共用一个队列:营销活动堵住了 OTP。
- 在用户请求内同步发送;服务商一慢,整个应用都慢。
- 不去重:worker 重启后,用户反复收到同一条消息。
- 对已失效的设备令牌无限重试,或者明明只是临时错误却不重试。
- 忽略用户偏好和免打扰时段,凌晨 3 点发通知。
- 关键渠道(OTP)只有一家服务商,它一挂就没人能登录。
- 不监控各渠道的队列延迟和失败率。
