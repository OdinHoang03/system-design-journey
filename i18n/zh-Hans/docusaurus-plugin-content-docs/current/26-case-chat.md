> 消息要发得快、顺序对,而且绝不能丢。

## 故事

NoteNest 的用户想直接在共享笔记上讨论。小明加上了聊天功能:一对一和小群。第一版是一个页面每 2 秒调用一次 `GET /messages`(轮询)。10 万人在线时,就是每秒 5 万个请求,几乎全是“没有新消息”的回答,而消息仍然最多延迟 2 秒。他需要一条始终打开的连接,让服务器能把消息*推*给接收者。

## 核心概念

### 1. 需求

**功能性:** 一对一和群聊(最多约 100 人);实时收发;历史记录;在线状态;多设备同步;(可选)已读回执。

**非功能性:** 低延迟(约 200 ms 以内)、**不丢消息**、同一会话内顺序一致、能容忍不稳定的网络。

**不在范围内:** 语音/视频通话、端到端加密。

### 2. 估算(取整,见第 8 课)

- 1000 万 DAU,每人每天 40 条消息 = 4 亿条/天 ≈ **4,600 条/秒**,峰值约 5 倍 ≈ **25,000 条/秒**。
- 每条约 100 字节加元数据 ⇒ 4 亿 × 100 B ≈ **40 GB/天**,≈ **15 TB/年**(未计副本)。
- 连接:10% 的 DAU 同时在线 = **100 万条长连接**。一台服务器大约能撑 5–10 万条空闲连接 ⇒ 需要 **约 20 台聊天服务器**。

结论:*写入*压力适中,真正决定架构的是**长连接的数量**。

### 3. 选择协议

| 方式 | 思路 | 缺点 |
|---|---|---|
| **轮询** | 客户端定期询问 | 浪费、延迟高 |
| **长轮询** | 服务器挂起请求直到有消息 | 不断重连;难以负载均衡 |
| **WebSocket** | 一条长期保持的双向 TCP 连接 | 有状态:必须知道用户连在哪台服务器 |
| **SSE** | 服务器通过 HTTP 单向推送 | 发送方向仍需单独请求 |

聊天的实时连接选 **WebSocket**,而非实时的操作(登录、加载历史、上传文件)仍走普通 HTTP API(第 9 课)。

### 4. 总体设计

![聊天系统](/img/diagrams/case-chat.svg)

*本项目自绘示意图。*

Alice 给 Bob 发消息的流程:

1. Alice 通过 WebSocket 发给**聊天服务器 A**,附带 App 生成的 `client_msg_id`。
2. 服务器 A **先把消息存入消息库**,再向 Alice 确认(ack)。先存后发:服务器中途宕机,消息也不会丢。
3. 服务器 A 查**注册表**(通常是 Redis:`user → server`)看 Bob 连在哪台服务器。
4. 如果 Bob 在服务器 B 上,A 通过内部通道(发布/订阅或直接调用)转给 B,B 再通过 Bob 的 WebSocket 推下去。
5. 如果 Bob 离线,消息已经在库里;发送**推送通知**(第 28 课),Bob 上线后 App 同步缺失的部分。

聊天服务器**不保存持久数据**,只保存连接。丢一台服务器,只是客户端重连到另一台。

### 5. 顺序与去重

- **顺序**:只需要*会话内*有序。为每个会话中的消息分配递增的 `seq`(存储中的计数器,或基于时间的 Snowflake 式 ID)。绝不要依赖客户端时钟。
- **去重**:网络不稳时客户端会重发。服务器用 `client_msg_id` 作为去重键,就像第 9 课的幂等键。
- **同步**:客户端记住收到的最大 `seq`,重连时问“把这个 `seq` 之后的全给我”。
- **确认**:消息有三种明确的状态:已存储、已送达设备、已读。不要混为一谈。

### 6. 存储

主要查询永远是“会话 X 最新的 N 条消息”和“`seq` Y 之后的消息”。按 `chat_id` 分区、按 `seq` 排序,更适合宽列存储(Cassandra、DynamoDB),而不是一张需要分片的巨大 SQL 表(第 5、12 课)。用户、群组、联系人数据仍放在 SQL 中。

### 7. 在线状态

服务器依靠**心跳**(客户端每 5–30 秒发一次)。超时没收到就视为离线,因为关闭标签页或信号丢失并不总会通知服务器。把在线状态存入带 TTL 的 Redis。不要向所有人广播“你的好友上线/下线了”;只发给正打开该会话或联系人列表的人,大群则改为拉取而不是推送。

### 8. 群聊

小群:按 `chat_id` 存**一份**消息,再向每个在线成员*扇出*(推送)。大群(成千上万人):只推送“有新消息”,让客户端自己拉取,类似第 25 课的大 V 问题。

## 取舍

| 选择 | 得到 | 失去 |
|---|---|---|
| WebSocket | 低延迟,几乎没有多余请求 | 服务器有状态,负载均衡更难,需处理重连 |
| 轮询 | 简单,易扩展 | 负载重,延迟高 |
| 先存后发 | 不丢消息 | 写入多一份延迟 |
| 先发后存 | 非常快 | 中途崩溃可能丢消息 |
| 按会话排序 | 便宜,够用 | 不同会话之间没有全局顺序 |
| 心跳判断在线 | 能应对突然断线 | 状态滞后几十秒,耗带宽 |
| 写时扇出(小群) | 投递快 | 大群代价高 |
| 读时拉取(大群) | 发送方成本低 | 接收方看到消息更晚 |

## 常见错误

- 用客户端时钟或多台服务器的 `NOW()` 给消息排序,顺序会乱。
- 先向发送者确认、后持久化,然后宕机:发送者以为发出去了,消息却丢了。
- 没有去重;弱网导致消息显示两次。
- 把重要状态放在聊天服务器内存里;一次部署就清空了。
- 每次有人重连就向整个联系人列表广播在线状态,造成事件风暴。
- 忘了批量部署时上百万客户端会同时重连(惊群);重连要带退避和抖动。
