> 数据库成了瓶颈,于是复制它、再把数据切开。

## 故事

有了缓存,NoteNest 顺利扛过了一波访问高峰。可几个月后,两件事同时发生:笔记数量涨到了数亿条,*写入*量也翻了好几倍。一天夜里,主数据库的磁盘坏了。小明从备份中恢复,服务中断了 40 分钟,最后 10 分钟的数据也彻底丢失。那一刻他明白了:数据库是**最难扩展**的部分,因为它保存着状态。

## 核心概念

### 第 0 步:先优化,再拆分

在复制或分片之前,先做那些成本更低的事:在合适的地方加**索引**,修复慢查询(`EXPLAIN`),使用连接池,加缓存(第 4 篇),升级机器配置。很多系统只靠一个精心维护的数据库,就能稳定支撑每秒数万次查询。

### 复制(Replication):多个副本

![Primary–replica](/img/diagrams/db-replication.svg)

*本图为本项目原创绘制;思路参考自 [donnemartin/system-design-primer](https://github.com/donnemartin/system-design-primer) (CC BY 4.0).*

最常见的模型是**主从复制(primary–replica,也叫 leader–follower)**:所有**写入**都进入主库(primary),主库把变更日志发送给各个从库(replica),**读取**则分散到从库上。

- 能做到:提升读取能力,有了备用节点(故障转移),还能在不影响用户的前提下跑耗资源的报表。
- 做不到:提升*写入*能力(所有写入仍然经过同一个主库),也不能扩大容量(每个从库仍要存放全部数据)。

**同步还是异步?**

| 类型 | 工作方式 | 取舍 |
|---|---|---|
| 异步 | 主库立即确认写入,从库随后跟上 | 速度快,但从库可能**落后**(复制延迟);如果主库宕机,最后几笔事务可能丢失 |
| 同步 | 主库等待从库确认 | 已确认的数据不会丢失,但写入更慢,而且一个从库挂掉就可能卡住写入 |
| 半同步 | 至少等待一个从库确认 | 在两者之间折中 |

**复制延迟**会引发令人头疼的问题:小兰修改了笔记,刷新页面,结果读到的是还没更新的从库,看到的竟是旧版本。解决办法:*读己之所写(read-your-writes)*,即用户刚写入后的几秒内从主库读取;或者只把可以接受略微过期数据的读请求发往从库。

**故障转移(Failover)**:主库宕机时,会将一个从库**提升**为新的主库。这要求能可靠地检测故障,并避免**脑裂(split brain)**,即两个节点都认为自己是主库。

除了主从复制,还有**多主(multi-leader)**(多个节点都能接收写入,必须处理冲突)和**无主(leaderless)**(Dynamo/Cassandra 风格,按 quorum 读写)。

### 分片(Sharding):切分数据

当一台机器再也装不下数据,或扛不住写入量时,我们就把数据**切分**成多个**分片(shard)**,每个分片是一个独立的数据库,只存放其中一部分数据。

![Sharding](/img/diagrams/db-sharding.svg)

*本图为本项目原创绘制;思路参考自 [Designing Data-Intensive Applications](https://dataintensive.net/) (M. Kleppmann),Partitioning 一章。*

关键决策是**分片键(shard key)**:

| 切分方式 | 示例 | 优点 | 缺点 |
|---|---|---|---|
| 按范围(range) | `user_id` 1–1M 放在分片 0 | 范围查询高效 | 容易出现**热点分片**(新用户都涌入最后一个分片) |
| 按哈希 | `hash(user_id) mod N` | 分布均匀 | 范围查询必须询问所有分片;改变 N 会让几乎所有数据搬家 |
| 一致性哈希 | 哈希环,每个分片负责一段弧 | 增减分片只需迁移一部分数据 | 更复杂;需要虚拟节点来保持均衡 |
| 按目录(directory) | “键 → 分片”的查找表 | 最灵活 | 查找表本身是需要保护和扩展的组件 |

对 NoteNest 来说,`user_id` 是天然的分片键:绝大多数查询只涉及单个用户,因此完全落在同一个分片内。

**分片的代价:**

- **跨分片查询**(join、全系统聚合)又慢又复杂。
- **跨分片事务**需要两阶段提交(two-phase commit)或 saga 这样的协议;通常最好通过数据设计让事务落在单个分片内,从而避免它。
- **重新分片(resharding)**(改变分片数量)是一个大工程。
- **热点 key**:某个“大 V”用户会让一个分片不堪重负,即使整体分布是均匀的。

实际上,每个分片还会有自己的从库;这两种技术是互补的。

### SQL 还是 NoSQL?

问题不是“哪个扩展得更好”,而是“你的数据模型和查询需要什么”。关系型数据库擅长处理关系、事务和灵活查询。许多 NoSQL 系统(key-value、文档型、宽列)舍弃了一部分功能,换来更容易切分和复制。两类系统都可以做复制和分片。

## 取舍

| 选择 | 收益 | 代价 |
|---|---|---|
| 异步复制 | 写入快,读取可扩展 | 从库有延迟;故障转移时可能丢失最后几笔事务 |
| 同步复制 | 数据安全 | 写入慢,可用性较差 |
| 分片 | 扩展写入和容量 | 跨分片查询/事务,运维复杂,重新分片代价高 |
| 按哈希分片 | 分布均匀 | 失去范围查询 |
| 按范围分片 | 范围查询友好 | 热点分片 |
| 范式化(normalize) | 重复少,一致性好 | join 多,难以切分 |
| 反范式化(denormalize) | 读取快,易于切分 | 更新时要修改多处 |

## 常见错误

- 过早分片,而其实只需要加索引和从库。
- 选了基数(cardinality)很低的分片键(例如国家),或单调递增的分片键(时间戳),造成热点分片。
- 把*所有*读请求都发往从库,结果遇到“刚保存完却看不到”的问题。
- 使用 `hash mod N` 之后又增大 N,导致几乎所有 key 都换了分片。
- 不演练故障转移;第一次真正跑起来,就是真出事故的时候。
- 把复制当成备份。`DROP TABLE` 命令同样会被复制过去。仍然需要定期备份,并演练恢复。

## 练习与面试题

1. 为 NoteNest 设计数据表结构并选择分片键。哪些查询会变成跨分片查询?
2. 解释复制延迟,并给出两种办法,避免用户刚写入后看到旧数据。
3. 主库宕机,从库 1 落后 2 秒,从库 2 落后 5 秒。提升哪一个?哪些数据可能丢失?
4. 新增一个分片时,比较 `hash(key) mod N` 和一致性哈希。
5. 如何处理一个拥有数千万粉丝的“热点用户”?
6. 什么情况下你*不*该分片?
