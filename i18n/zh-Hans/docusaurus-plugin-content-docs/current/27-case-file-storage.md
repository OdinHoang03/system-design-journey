> 大文件不该绕道经过你的服务器。

## 故事

NoteNest 的用户想在笔记里附上照片、PDF,甚至 2 GB 的讲课视频。小明的第一版通过 API 接收文件,再写到 App 服务器的磁盘上。一个人上传大视频就占着连接好几分钟;三个人一起上传,worker 就耗尽了。磁盘很快写满,加服务器后文件只在这台机器上,别的机器看不到。网络在 95% 时掉线,就得从头再传。是时候把文件当作一个独立的问题来对待了。

## 核心概念

### 1. 需求

**功能性:** 上传和下载文件(最大几 GB);掉线后续传;多设备同步;任何网络下流畅播放视频;链接分享;版本历史(可选)。

**非功能性:** **高持久性**(存好的文件绝不能丢)、全球快速分发、存储成本合理。

**不在范围内:** 实时协同编辑文档。

### 2. 估算(见第 8 课)

- 500 万 DAU,10% 每天上传,平均 5 MB ⇒ 50 万 × 5 MB ≈ **2.5 TB/天**,≈ **900 TB/年**;3 副本约 2.7 PB。这就是必须用对象存储而不是服务器磁盘的原因。
- 写入:50 万个文件/天 ≈ **6 个文件/秒**,很小。问题在带宽:2.5 TB/天 ≈ 平均 **30 MB/s**,峰值是其数倍。
- 读取:是写入的 10–50 倍,主要是视频和图片 ⇒ 需要 **CDN**(第 2 课)。

结论:文件数量不多,但**容量和带宽巨大**。不要让文件字节经过 App 服务器。

### 3. 元数据与内容分离

| 部分 | 存放位置 | 原因 |
|---|---|---|
| **文件内容**(字节) | **对象存储**(S3 或同类),切成分块 | 便宜、持久(多副本)、几乎无限扩展 |
| **元数据**(名称、所有者、大小、分块列表、版本、权限) | 数据库(SQL,第 5、12 课) | 需要查询、事务、访问控制 |

### 4. 总体设计

![文件与视频存储](/img/diagrams/case-file-storage.svg)

*本项目自绘示意图。*

1. 客户端调用**开始上传**;元数据服务创建一条 `uploading` 记录,并为每个分块返回**预签名 URL**(带签名、几分钟后过期)。
2. 客户端用这些 URL **把每个分块直接 PUT 到对象存储**,字节不经过 App 服务器。多个分块可并行上传。
3. 完成后,客户端(或存储事件)通知**提交**;元数据服务确认分块齐全,把状态改为 `ready`。
4. 对于视频,提交会把任务放入**队列**(第 6 课);worker **异步转码**。
5. 结果(多种分辨率)由 **CDN** 提供给观看者。

### 5. 分块

把文件切成分块(比如 4–8 MB)带来:

- **可续传**:只重传缺失的分块。
- **并行**:多个分块同时上传,充分利用带宽。
- **同步省流量**:修改大文件的一部分,只需上传变化的分块(比较分块哈希)。
- **去重**:哈希相同的分块只存一份。

分块太小会让元数据膨胀、请求数增多;太大又会失去续传和并行的好处。

### 6. 多设备同步

每台设备记住一个 `version`/游标;联网后问“这个游标之后有什么变化?”(长轮询,或推送通知告知有变化后再拉取变更列表)。两台设备同时修改一个文件会产生**冲突**:简单的做法是两份都留下(“冲突副本”),自动合并只适合结构化数据。

### 7. 视频:转码与流式播放

原始视频(单一格式、单一码率)无法在所有设备上流畅播放。worker 把它**转码**成多种分辨率/码率,再切成几秒长的小段(HLS 或 MPEG-DASH)。播放器根据当前带宽选择片段(**自适应码率**),网络变化时切换画质。转码很吃 CPU,所以通过队列异步执行,并按队列长度扩缩 worker;处理完成前用户看到“处理中”。

### 8. 分发与安全

- **CDN** 在离观看者近的地方缓存视频片段和公开文件(第 2、4 课)。
- 私有下载在元数据服务校验权限后,使用**短期预签名 URL**,而不是公开存储桶。
- 在状态变为 `ready` 之前,异步做病毒/内容扫描。
- 生命周期:把很少访问的文件转到更便宜的存储层,清理被放弃上传留下的孤儿分块。

## 取舍

| 选择 | 得到 | 失去 |
|---|---|---|
| 直传对象存储 | App 服务器轻,扩展好 | 要管理签名 URL,上传后需校验 |
| 经过 App 服务器 | 控制严格,起步简单 | 带宽瓶颈,连接占用久 |
| 小分块 | 续传和同步更精细 | 元数据多,请求多 |
| 大分块 | 请求少 | 失败时重传多,同步粗糙 |
| 去重 | 省空间 | 复杂,删除时要引用计数,有隐私顾虑 |
| 异步转码 | 不阻塞用户,独立扩展 | 视频不能立刻观看 |
| 多种分辨率 | 任何网络都流畅 | 存储和 CPU 成本 |
| 冲突时两份都留 | 不丢数据 | 用户要手动合并 |

## 常见错误

- 让文件字节先经过 App 服务器再到存储。
- 没有可续传上传;2 GB 的文件在 95% 失败就得重来。
- 把存储桶设为公开而不用签名 URL,私有文件泄露。
- 预签名 URL 有效期过长,或没有大小/类型限制。
- 在上传请求里同步转码,请求超时。
- 删了元数据却没删分块(垃圾无限增长),或者删了仍被引用的分块。
- 相信客户端声明的扩展名/`Content-Type`;必须真正校验。
