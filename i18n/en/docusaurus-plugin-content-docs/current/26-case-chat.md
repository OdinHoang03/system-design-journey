> Messages must arrive fast, in order, and never get lost.

## Story

NoteNest users want to discuss right on shared notes. Minh adds chat: 1-1 and small groups. The first version is a page calling `GET /messages` every 2 seconds (polling). With 100,000 people online that is 50,000 requests per second, nearly all answering "nothing new", and messages are still up to 2 seconds late. He needs an always-open connection so the server can *push* to the recipient.

## Core concepts

### 1. Requirements

**Functional:** 1-1 and group chat (up to ~100 people); real-time send/receive; history; online status; multi-device sync; (optional) read receipts.

**Non-functional:** low latency (under ~200 ms), **no lost messages**, consistent order within a conversation, tolerance for flaky networks.

**Out of scope:** voice/video calls, end-to-end encryption.

### 2. Estimation (rounded, see lesson 8)

- 10M DAU, 40 messages each per day = 400M messages/day ≈ **4,600 msg/s**, peak ~5× ≈ **25,000/s**.
- ~100 bytes + metadata each ⇒ 400M × 100 B ≈ **40 GB/day**, ≈ **15 TB/year** (before replication).
- Connections: 10% of DAU online at once = **1 million open connections**. One server holds roughly 50,000–100,000 idle connections ⇒ **~20 chat servers**.

Conclusion: the *write* load is moderate, but the **number of long-lived connections** is what shapes the architecture.

### 3. Choosing a protocol

| Option | Idea | Downside |
|---|---|---|
| **Polling** | Client asks periodically | Wasteful, slow |
| **Long polling** | Server holds the request until there is a message | Constant reconnecting; hard to load-balance |
| **WebSocket** | One long-lived two-way TCP connection | Stateful: you must know which server a user is on |
| **SSE** | Server pushes one-way over HTTP | Sending still needs separate requests |

Chat uses **WebSocket** for the real-time connection, while non-real-time operations (login, loading history, uploading files) still go through ordinary HTTP APIs (lesson 9).

### 4. High-level design

![Chat system](/img/diagrams/case-chat.svg)

*Original diagram drawn for this project.*

Flow when Alice sends Bob a message:

1. Alice sends over WebSocket to **chat server A**, with a `client_msg_id` generated by the app.
2. Server A **persists the message to the message store** first, then acknowledges to Alice. Store first, deliver after: if the server dies midway the message is not lost.
3. Server A looks in the **registry** (typically Redis: `user → server`) to find which server Bob is on.
4. If Bob is on server B, A forwards the message over an internal channel (pub/sub or direct call) to B, which pushes it down Bob's WebSocket.
5. If Bob is offline, the message already sits in the store; send a **push notification** (lesson 28), and when Bob comes back the app syncs what it missed.

Chat servers hold **no durable data**, only connections. Losing one just makes clients reconnect to another.

### 5. Ordering and de-duplication

- **Ordering**: you only need order *within a conversation*. Assign each message an increasing `seq` per conversation (a counter in the store, or a time-based Snowflake-style ID). Never rely on client clocks.
- **De-duplication**: on a flaky network the client resends. The server uses `client_msg_id` as a dedup key, like the idempotency key in lesson 9.
- **Sync**: the client remembers the highest `seq` it received; on reconnect it asks "give me everything after this `seq`".
- **Acks**: a message has three distinct states: stored, delivered to a device, read. Do not merge them.

### 6. Storage

The main queries are always "latest N messages of conversation X" and "messages after `seq` Y". Partitioning by `chat_id`, sorted by `seq`, fits a wide-column store (Cassandra, DynamoDB) better than one huge SQL table you must shard (lessons 5, 12). User, group and contact data stays in SQL.

### 7. Online presence

Servers rely on a **heartbeat** (the client sends one every ~5–30 seconds). If none arrives in time, the user is offline, because closing a tab or losing signal does not always notify the server. Store presence in Redis with a TTL. Do not broadcast "your friend went online/offline" to everyone; send it only to people with that conversation or contact list open, and for large groups pull instead of push.

### 8. Group chat

Small groups: store **one** copy of the message under `chat_id`, then *fan out* (push) to each online member. Large groups (thousands): push only "new message available" and let clients pull, similar to the celebrity problem in lesson 25.

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| WebSocket | Low latency, few wasted requests | Stateful servers, harder load balancing, reconnect handling |
| Polling | Simple, easy to scale | Heavy load, latency |
| Store then deliver | No lost messages | Extra write latency |
| Deliver then store | Very fast | May lose messages if it crashes midway |
| Per-conversation ordering | Cheap, sufficient | No global order across conversations |
| Heartbeat presence | Survives abrupt disconnects | Status lags by tens of seconds, costs bandwidth |
| Fan-out on write (small groups) | Fast delivery | Expensive for large groups |
| Pull on read (large groups) | Cheap for the sender | Recipients see messages later |

## Common mistakes

- Ordering messages by client clock or by `NOW()` on several servers; order gets scrambled.
- Acknowledging the sender before persisting, then crashing: the sender thinks it was sent, the message is lost.
- No de-duplication; a weak network makes messages appear twice.
- Keeping important state in a chat server's memory; a deploy wipes it.
- Broadcasting presence to the whole contact list every time someone reconnects; event storms.
- Forgetting that during a mass deploy a million clients reconnect at once (thundering herd); reconnect with backoff and jitter.
